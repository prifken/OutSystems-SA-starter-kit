# Requirement Document Builder for OutSystems ODC

A skill for helping developers and technical leads create and improve requirement documents that serve as specifications for OutSystems ODC app generation.

## When to use this skill

Use this skill when:
- A user wants to draft a requirement document for a new app from scratch
- A user has an existing requirement doc they want to validate or improve
- A user needs help structuring entity definitions, data models, or access control specs
- A user needs examples or templates to follow the ODC requirement document format
- A user wants to ensure their spec is complete enough for app generation to succeed

## Supported input formats and limits

Mentor Web accepts requirement documents in the following formats:

- `.md` (Markdown) — **preferred output format for this skill**
- `.docx` (Word)
- `.pdf`
- `.txt`

Maximum file size: **5 MB**.

> **Output convention**: This skill always produces requirement documents as `.md` files. All other formats are valid for upload to Mentor Web but are not generated by this skill.

## What this skill does

### Mode 1: Interactive creation (from scratch)

When the user wants to build a requirement document from the ground up:
1. Start with high-level intent: What's the business problem? Who are the users?
2. **Ask about language**: What is the operational language of the app? (e.g. Dutch, French, English). Do not assume — always ask if not explicitly stated.
3. Ask focused questions about the data model: What entities? What relationships?
4. Clarify roles and permissions: Who does what?
5. Understand the main screens and features: What does the UI need?
6. **Capture theme & branding** (required): What visual theme, primary/secondary colors, and logo should the app use? If the client has a website or brand assets, offer to extract colors from them. Do not leave as default.
7. **Identify business logic**: Are there status workflows, auto-calculations, SLA rules, scheduled processes, or approval flows? If yes, document them in a Business Logic section.
8. **Confirm out of scope**: What should the app explicitly NOT do? List these to prevent scope creep.
9. **Note open points**: Are there any unresolved questions (e.g. integration details, SSO protocol, exact status values)? Capture them in an Open Points section rather than silently assuming answers.
10. Optionally capture external integrations or special requirements
11. Synthesize responses into a complete requirement document
12. Save as a markdown (.md) file and present via `present_files`

### Mode 2: Full audit of existing documents

When the user provides an existing requirement document:
1. **Structure check**: Verify all required sections are present: app overview, theme & branding, data model, roles & permissions, screens & features, business logic (if non-trivial), out of scope, open points
2. **Language convention check**:
   - App Overview must be written in English — flag if it is in any other language
   - All other sections must be in the app's operational language — flag mixed-language sections
3. **Theme & branding check**: Verify that primary/secondary colors are specified as hex values, typography is named, and theme is not left as "default ODC theme" without specification
4. **Quality audit**: Check that:
   - All entity attributes have explicit data types (Text, Identifier, Boolean, DateTime, Currency, Integer, Email, PhoneNumber, UserIdentifier)
   - Relationships are clearly stated (One-to-Many, Many-to-Many, or Foreign Key references)
   - Roles include entity-level access levels (Edit, View, Full)
   - Row-level rules name the specific field that enforces them
   - Screen descriptions specify layout types where relevant (table, gallery, master-detail, card list, map)
   - Dashboard specs list concrete chart/counter types, not generic requests
   - Business logic rules (status transitions, calculations, scheduled processes) are captured in a dedicated section, not buried in screen descriptions
   - Out of scope is explicitly stated — flag if absent
   - Open points are surfaced as named items, not silently resolved with assumptions
   - Language is specific and unambiguous (avoid "user-friendly", "intuitive", "flexible")
5. **ODC-specific checks**: Flag any issues that would cause problems during generation (missing data types, unclear relationships, PII in examples, features outside ODC scope)
6. Present findings using the three-tier format (🔴 Red / 🟡 Yellow / 🟢 Green) and offer a revised version

## Structure reference

Every requirement document should include these sections. The **Required** column reflects OutSystems' official guidance; **Convention** marks additions established as working practice across engagements that go beyond the official minimum.

| Section | Required | Source | Purpose |
| --- | --- | --- | --- |
| **App Overview** | Yes | OutSystems | 1-2 paragraphs in **English**, regardless of the app's operational language. Describes the business problem, desired outcome, and key users. |
| **Theme & Branding** | Yes | Convention | Visual theme, primary/secondary colors (hex values), typography, logo. Must be specified explicitly — never left as default. Extract from client website or uploaded screenshot if not provided. *(OutSystems lists this as optional "General app settings"; we treat it as required.)* |
| **Localization & Accessibility** | No | OutSystems | Language settings, date/time format, timezone, WCAG level |
| **Data Model** | Yes | OutSystems | Entities with attributes (including data types), relationships, static entities |
| **Roles & Permissions** | Yes | OutSystems | Defined roles with entity-level access levels and row-level rules |
| **Main Features & Screens** | Yes | OutSystems | List of screens with layout types and UX requirements |
| **Business Logic & Workflows** | Yes (if non-trivial) | Convention | Status transition rules, auto-calculations, scheduled processes, validation logic that goes beyond simple CRUD. Required when the app has approval flows, SLA logic, auto-generated identifiers, or multi-step workflows. *(OutSystems covers this under "Include: Business logic and workflows" without a dedicated section; we surface it explicitly.)* |
| **Out of Scope** | Yes | Convention | Explicit list of what the app does NOT cover. Prevents scope creep and clarifies boundaries for generation. *(Not in OutSystems official structure; added as a working convention.)* |
| **Open Points** | No | Convention | Unresolved questions that must be answered before or during build. Preserve ambiguities here rather than resolving them silently with assumptions. |
| **External Integrations** | No | OutSystems | Data sources, system dependencies, Data Fabric connections |

### Language convention

- **App Overview is always written in English**, regardless of the client's operational language. This is a fixed convention across all ODC requirement documents.
- **All other sections are written in the app's operational language** (e.g. Dutch for nl-NL/nl-BE clients, French for fr-BE clients).
- **When the app language is unclear, always ask explicitly before writing** — do not assume based on client name, location, or document context.

## Data types reference

When defining entity attributes, use these types:
- **Identifier**: Primary keys, foreign keys, bridging entities
- **Text**: Names, descriptions, addresses, notes
- **Boolean**: True/false flags (IsActive, RequiresApproval)
- **DateTime / Date**: Timestamps, deadlines, scheduled dates
- **Currency**: Monetary values, fees, totals
- **Integer**: Quantities, counts, rankings
- **Email**: Email addresses
- **Phone Number**: Phone contacts
- **User Identifier**: References to OutSystems users/identities

## What to include and what to avoid

### Include:

| What | Why | Example |
| --- | --- | --- |
| **Entity definitions with data types** | ODC generates fields based on types; missing types cause wrong field types (text instead of email, etc.) | Customer.Email: Email type → generates email validation |
| **Explicit relationships** | Unclear relationships break data model generation; many-to-many needs bridging entities | "Order has many OrderItems" with explicit Foreign Keys |
| **Functional requirements & workflows** | Explains what the app does and in what sequence; helps with screen flow and business logic | "Users complete multi-step approval workflow: Draft → Submitted → Reviewed → Approved" |
| **Specific UI layouts** | Generic "List" generates Table by default; specifying layouts ensures UX matches intent | "Product Gallery view: card-based, showing image, name, price, with search filter" |
| **Dashboard specifications with chart types** | Vague "metrics" generates placeholder UI; concrete specs generate usable dashboards | "Counter: Total Sales, Line Chart: Sales by Month, Bar Chart: Top 5 Products" |
| **Business rules & validations** | Ensures data integrity is enforced in generated app, not added later manually | "Order.Total must be > 0", "Email must be unique", "DueDate cannot be in the past" |
| **Entity-level and row-level access** | Row-level rules prevent data leakage and enforce security at generation time | "Employee can only edit Tasks where AssignedToId = CurrentUser" |
| **Static entity records** | Enumerations must be complete; ODC generates dropdowns from these values | OrderStatus: Pending, Confirmed, Processing, Shipped, Delivered, Cancelled (all 6 values) |

### Avoid:

| What | Why | Impact |
| --- | --- | --- |
| **Real personal data (PII)** | Exposes confidential information; violates privacy best practices; complicates later data anonymization | Use John.Doe@example.com, not john.doe@yourcompany.com |
| **Implementation code** | ODC generates code from the spec; implementation details are irrelevant and confusing | Don't include SQL queries, API endpoints, or pseudo-code |
| **Complex tables** | Mentor Web can't reliably parse multi-column tables; content may be misread or skipped | Use bullet lists and plain text instead of tables with many columns or merged cells |
| **Screenshots or embedded images** | ODC can't process visual content; these bloat the spec without adding value | Instead of a screenshot, describe: "Table with columns: Name, Email, Active checkbox, with sort and filter" |
| **Vague language** | Words like "intuitive" can't be translated to screen layouts or features | "User-friendly order entry" → "Order Entry Form with auto-calculated totals and field validation" |
| **Ambiguous relationships** | ODC can't determine if it's One-to-Many, Many-to-Many, or needs a bridge entity | "Product has many Prices" → clarify: One current price per product? Historical price records? |
| **Missing data types** | ODC assumes Text type, leading to no validation, wrong UI widgets, incorrect sorting behavior | StartDate without "Date" type renders as text field with no date picker |
| **Open-ended static entity lists** | "Status values: Pending, Confirmed, ... and others as needed" means ODC generates incomplete dropdowns | List all status values upfront; new ones can be added later if business rules change |
| **Features outside ODC scope** | ODC generates standard CRUD apps and dashboards; AI, analytics, or advanced integrations require custom code | "Generate a real-time ML recommendation engine" can't be built by app generation alone |

## Example patterns

### Entity with relationships
```
Entity: Order
Attributes:
- Id: Identifier (Primary Key)
- OrderNumber: Text (auto-generated unique ID)
- OrderDate: DateTime
- CustomerId: Identifier (Foreign Key to Customer)
- StatusId: Identifier (Foreign Key to OrderStatus)

Relationships:
- Customer has many Orders (One-to-Many)
- Order has many OrderItems (One-to-Many)
```

### Static entity (lookup)
```
Entity: OrderStatus
Purpose: Defines order lifecycle states
Records: Pending, Confirmed, Processing, Shipped, Delivered, Cancelled
```

### Role with permissions
```
Role: Sales Rep
- Order: Edit Access
- OrderItem: Edit Access
- Customer: View Access
- Product: View Access
```

### Dashboard spec
```
Dashboard: Sales Overview
- Total Revenue (Counter)
- Pending Orders (Counter)
- Orders by Status (Donut Chart)
- Revenue by Month (Bar Chart)
```

## Interaction patterns

**When creating from scratch:**
Ask focused questions one or two at a time. Build progressively. Once you understand the core business problem, data entities, and user roles, you have enough to draft an initial doc. Then present it for refinement.

**When validating:**
Present findings in three tiers: 
1. Red flags (blockers for generation)
2. Yellow flags (quality issues)
3. Green suggestions (nice-to-haves)

Offer a revised version incorporating feedback, ready to use or iterate further.

**File output:**
The output format for all requirement documents is always a markdown (`.md`) file — never DOCX, PDF, or plain text. Do not ask the user whether they want a markdown file; always produce one. Once the document reaches a stable version, write it to a `.md` file and present it via `present_files`.

## Requirement Documents vs. Direct Prompts

**Requirement documents (this skill)** are best for:
- Complex apps with many entities, relationships, and roles
- Apps requiring clear upfront planning before generation
- Teams that need standardized, reviewed specifications
- First-time ODC users who benefit from structured guidance
- Apps where multiple stakeholders need to align on requirements

**Direct Mentor Web prompts** are best for:
- Quick prototypes and MVPs with few entities
- Iterative refinement (prompt → generate → review → refine)
- UI/UX pattern changes (using Mentor Web's pattern library)
- Developers who prefer conversational, exploratory iteration
- Adding features to existing generated apps

**Hybrid approach** (recommended):
1. Use this skill to draft a requirement document upfront
2. Generate the app with Mentor Web using the requirement doc
3. Refine the generated app with Mentor Web direct prompts for UI patterns, themes, data model tweaks
4. Transition to ODC Studio for advanced customization beyond agentic development

For detailed UI pattern prompts and Mentor Web-specific guidance, see the **Mentor Web Prompts Cookbook** referenced below.

## Common Mistakes to Prevent

Watch for these pitfalls when creating or reviewing requirement documents. Flag them immediately:

### 1. Missing or Vague Data Types
**Problem**: "Employee has a Name, Email, and StartDate" (no types specified)
**Impact**: ODC generates incorrect fields, no email validation, possible data integrity issues
**Solution**: Require: Name: Text, Email: Email, StartDate: Date

### 2. Forgetting Primary Keys & Foreign Keys
**Problem**: Entities defined without Id fields or relationship IDs
**Impact**: Can't generate unique entity records; relationships fail
**Solution**: Every entity needs an Id (Identifier). Every relationship needs a Foreign Key field.

### 3. Many-to-Many Without Bridging Entity
**Problem**: "Students have Courses" (M-to-M) defined as a simple relationship
**Impact**: ODC can't generate the proper database structure
**Solution**: Create StudentCourse bridging entity with StudentId and CourseId foreign keys

### 4. Vague Language That Can't Be Generated
**Problem**: "The app should be intuitive and user-friendly"
**Impact**: Non-actionable guidance; ODC generates generic default UI
**Solution**: Replace with specifics: "Task list uses Table layout with columns for Title, Status, Assignee, and DueDate"

### 5. Incomplete Static Entity Records
**Problem**: OrderStatus: "Pending, Confirmed, ... and other statuses as needed"
**Impact**: ODC can't generate complete dropdown menus; values must be added later manually
**Solution**: List ALL possible status values upfront

### 6. Role Permissions Without Access Levels
**Problem**: "HR can manage employees, Finance can view reports"
**Impact**: Unclear if roles have Edit or View access; generation may apply overly broad or restrictive permissions
**Solution**: Specify Edit, View, or Full for every role-entity pair

### 7. Row-Level Rules Without Enforcement Field
**Problem**: "Employees see only their own tasks" (no mention of which field enforces this)
**Impact**: Unclear how to filter data; row-level security not generated
**Solution**: Explicit rule: "Task.AssignedToId = CurrentUser" or "Task.CreatedBy = CurrentUser"

### 8. Screens Without Layout Types
**Problem**: "Product List screen and Product Detail screen"
**Impact**: ODC defaults to Table layout for all screens; may not match your UX intent
**Solution**: Specify: "Product List (Table layout with Name, SKU, Price, Category columns)" and "Product Detail (Master-Detail with form and line items)"

### 9. Dashboards With Generic Requests
**Problem**: "Sales Dashboard showing key metrics and trends"
**Impact**: ODC generates placeholder UI; you don't know what charts it will create
**Solution**: Be explicit: "Counter for total sales, Line chart for sales by month, Bar chart for sales by region"

### 10. PII in Example Data
**Problem**: Using real employee names, email addresses, or phone numbers in the spec
**Impact**: Confidential information exposed in documentation and shared specs
**Solution**: Use fictional/placeholder data: "John Doe, john.doe@example.com" (clearly fictional)

### 11. App Overview Not in English
**Problem**: App Overview written in Dutch, French, or another operational language
**Impact**: Breaks the fixed language convention; creates inconsistency across the document portfolio
**Solution**: Always write the App Overview in English. All other sections follow the app's operational language.

### 12. App Language Assumed Instead of Asked
**Problem**: Language chosen based on client name or assumed context (e.g. "Belgian client → Dutch") without explicit confirmation
**Impact**: Wrong language used; nl-BE vs nl-NL distinction missed; French-speaking Belgian clients receive Dutch documents
**Solution**: Always ask the user explicitly: "What is the operational language of this app?" before writing any section other than App Overview.

### 13. Theme Left as Default
**Problem**: Theme section says "use the default ODC theme" or is missing entirely
**Impact**: Generated app uses generic OutSystems styling with no brand alignment; costly to retheme after generation
**Solution**: Always specify primary and secondary colors as hex values, typography, and any logo or style reference. If the client has a website, extract colors from it (fetch the site or pixel-sample a screenshot). Never leave theme unspecified.

### 14. Business Logic Buried in Screen Descriptions
**Problem**: Status transition rules, SLA calculations, auto-generated identifiers, or scheduled processes described inline within a screen spec
**Impact**: ODC may not generate the logic correctly; hard to audit; logic may be missed entirely
**Solution**: Create a dedicated Business Logic & Workflows section. Move all rules, calculations, transitions, and scheduled processes there. Screen specs should reference the rule by name, not re-describe it.

### 15. Out of Scope Not Stated
**Problem**: No explicit list of what the app does not cover
**Impact**: Scope creep during build; ambiguity about what Mentor Web should or should not generate; stakeholder misalignment
**Solution**: Always include an Out of Scope section listing adjacent systems, features, or processes that are explicitly excluded. Even a short list of 3–5 items prevents misunderstandings.

### 16. Open Points Silently Resolved
**Problem**: Ambiguities (e.g. unknown SSO protocol, unconfirmed status values, unclear integration direction) resolved by assumption rather than flagged
**Impact**: Generated app may embed incorrect assumptions; client discovers problems post-generation; rework required
**Solution**: Capture every unresolved question in an Open Points section with a clear label (e.g. "OPEN PUNT" or "⚠ Open"). State what is unknown, why it matters, and who is responsible for resolving it before build starts.

**When you spot these during creation or validation, stop and fix them before proceeding.**

## ODC-specific notes

### Data Fabric & Integrations
- Data Fabric connections must exist in ODC before generation — if external integrations are specified, note which connections need to be pre-configured
- Document the direction of data flow (read-only vs. read-write)
- Note any data freshness requirements (real-time vs. batched sync)

### Data Type Specificity
- **Missing data types = generation failure or silent defaults**: ODC won't guess whether a field should be Text or Email. Be explicit.
- **Common pitfall**: Using "Text" for data that should be Currency, Integer, Date, or Email. This results in incorrect validation and UI widgets.
- **Solution**: Use the data type reference table above; when in doubt, ask the user.

### Static Entities (Lookups)
- Static entities define lookups and enumerations — always include their purpose and record list
- ODC generates these as dropdowns in forms; you MUST define all possible values upfront
- **Common pitfall**: Adding new status values after generation; plan for all variations in advance

### Relationships & Bridging Entities
- Many-to-Many relationships require a bridging entity (e.g., StudentCourse bridges Student and Course)
- **Common pitfall**: Saying "Employee has Skills" without clarifying: is it One-to-Many (employee has multiple skills) or a bridge table (employees and skills have complex assignment rules)?
- When in doubt, default to a bridging entity with explicit attributes (e.g., EmployeeSkill with AssignedDate, ProficiencyLevel)

### Row-Level Rules in Permissions
- Row-level rules must be **specific and enforceable**: "Users can view records they created" works; "authorized users" does not
- Common patterns:
  - Ownership-based: `CreatedBy = CurrentUser`
  - Department-based: `Employee.Department = CurrentUser.Department`
  - Manager approval: `ApprovedBy <> null`
- **Common pitfall**: Forgetting to specify which field enforces the rule (e.g., EmployeeId, CreatedBy, DepartmentId)

### Screen Layouts & UX Hints
- Specifying layouts helps ODC generate appropriate UI:
  - **Table**: Best for searchable lists with filters; supports sorting and bulk actions
  - **Gallery/Card**: Best for visual browsing; supports filtering but not fine-grained sorting
  - **Master-Detail**: Best for hierarchical data (parent record with child list)
  - **Form**: Best for data entry or single-record detail view
- **Common pitfall**: Saying "List screen" without specifying layout; ODC defaults to table, which may not suit your UX
- Include filter and sort column hints to guide generation

### Dashboard Specifications
- **Common pitfall**: Vague specs like "Show inventory" without metrics. Be specific:
  - Bad: "Inventory Dashboard"
  - Good: "Counter showing total inventory value, Bar chart showing quantity by warehouse, Donut chart showing quantity by product category"
- **Chart type matters**: Counters for single metrics, Bar/Column for comparisons, Donut/Pie for proportions, Line for trends over time
- Row-level filtering: Specify if managers see all data or filtered by department/warehouse

### Field Validations & Business Rules
- Include validation rules in the requirement doc if they're non-obvious:
  - Email fields: validation automatic in ODC
  - Currency fields: specify rounding rules if needed
  - Dates: specify if future dates are allowed, date range constraints
  - Unique fields: explicitly mark SKU, Email, or other unique identifiers
- **Common pitfall**: Assuming ODC will enforce business rules (e.g., "Order total = sum of line items") without specifying them

## Pre-Generation Readiness Checklist

Before handing a requirement doc to ODC for generation, verify:

### Data Model ✓
- [ ] Every entity has an Id field (Identifier, Primary Key)
- [ ] Every attribute has an explicit data type (no bare nouns like "name" without "Text")
- [ ] All Foreign Keys are explicit (e.g., EmployeeId: Identifier, FK to Employee)
- [ ] All relationships are declared (One-to-Many, Many-to-Many with bridging entity)
- [ ] Static entities list all possible values (no "TBD" or open-ended lists)
- [ ] No PII in example data (use fictional names, emails, phone numbers)

### Roles & Permissions ✓
- [ ] All roles specified by name
- [ ] Each role lists entity access levels: Edit, View, or Full
- [ ] Row-level rules are specific and include the field that enforces them
- [ ] No vague language like "authorized users" or "appropriate access"
- [ ] Relationship between roles and user types is clear (e.g., Managers have Manager role, etc.)

### Screens & Features ✓
- [ ] Every screen has a name, purpose, and layout type (Table/Form/Card/Master-Detail)
- [ ] Table screens list column names and filter options
- [ ] Master-detail screens identify parent and child entities
- [ ] Dashboard screens list concrete chart/counter elements with types
- [ ] No generic descriptions (e.g., "user-friendly", "intuitive", "flexible")
- [ ] Forms specify required vs. optional fields

### ODC Integration ✓
- [ ] Data Fabric connections pre-configured in ODC if specified
- [ ] Direction of external data flow documented (read/write/sync frequency)
- [ ] No dependencies on features outside ODC scope (advanced analytics, ML, custom code)

### Language & Clarity ✓
- [ ] App Overview is written in English
- [ ] All sections other than App Overview are in the app's operational language
- [ ] App language was confirmed explicitly — not assumed
- [ ] No ambiguous words (check for "flexible", "appropriate", "intuitive", "simple")
- [ ] All abbreviations defined on first use (e.g., "SKU (Stock Keeping Unit)")
- [ ] Technical terms used consistently (don't say "order status" and "order state" interchangeably)
- [ ] Examples given in entity definitions are fictional, not real data

### Theme & Branding ✓
- [ ] Primary and secondary colors specified as hex values (not "blue" or "brand color")
- [ ] Typography named (font family and fallback)
- [ ] Colors extracted from client website or brand assets — not left as ODC default
- [ ] Status/alert colors defined (success, warning, error) if the app uses SLA or workflow states

### Business Logic & Scope ✓
- [ ] All status transition rules documented in a Business Logic section (not scattered in screen specs)
- [ ] All auto-calculations and scheduled processes described as business rules, not implementation code
- [ ] Out of Scope section present with at least 3 explicit exclusions
- [ ] Open Points section present for every unresolved question; each item names the responsible party
- [ ] No open points silently resolved with assumptions

### Output Format ✓
- [ ] Document is saved as a `.md` file (not DOCX, PDF, or plain text)
- [ ] File is presented via `present_files`

**Tip**: Before finalizing, read the doc as if you're ODC and you have no context beyond these words. Would you understand how to build it?
